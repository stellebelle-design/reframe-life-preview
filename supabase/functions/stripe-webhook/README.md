# Preview Stripe webhook setup

This function belongs to the Reframe Life **preview** project only.

## 1. Apply the database migration

In the Supabase preview project `mzzujnceyspsvlbllzst`, open SQL Editor and run the contents of:

`supabase/migrations/20261119_client_purchase_payment_tracking.sql`

This adds the Stripe PaymentIntent reference used to revoke access after a full refund.

## 2. Deploy the function

Deploy `supabase/functions/stripe-webhook/index.ts` to the preview project as an Edge Function named `stripe-webhook`.

Stripe does not send a Supabase user JWT. Deploy with JWT verification disabled for this function only:

```sh
supabase functions deploy stripe-webhook --project-ref mzzujnceyspsvlbllzst --no-verify-jwt
```

Do not disable JWT verification on any other function.

## 3. Configure Edge Function secrets

In Supabase Dashboard → Edge Functions → Secrets, make sure these secrets are available to the function:

- `STRIPE_SECRET_KEY`: the preview Stripe **test-mode** secret key (same key family used by the existing checkout function).
- `STRIPE_WEBHOOK_SECRET`: the signing secret generated by the Stripe webhook endpoint in step 4.
- `PROJECT_SERVICE_ROLE_KEY`: the preview project's service-role key, matching the existing deployed webhook's environment variable. Keep it server-side; never put it in website JavaScript or commit it to GitHub.
- `PROJECT_URL`: the preview project's Supabase URL, matching the existing deployed webhook's environment variable.

Supabase provides `SUPABASE_URL` to Edge Functions. Do not add secrets to the repository.

## 4. Add the endpoint in Stripe test mode

In Stripe Dashboard, switch to **Test mode**, then add a webhook endpoint:

`https://mzzujnceyspsvlbllzst.supabase.co/functions/v1/stripe-webhook`

Subscribe to these events:

- `checkout.session.completed`
- `checkout.session.async_payment_succeeded`
- `customer.subscription.updated`
- `customer.subscription.deleted`
- `charge.refunded`

Copy the endpoint's signing secret (starts with `whsec_`) into Supabase as `STRIPE_WEBHOOK_SECRET`.

## 5. What the handler does

- Verifies every request using Stripe's webhook signature before processing it.
- Creates/updates the purchase record using the user and product metadata placed on the Checkout Session by the existing checkout function.
- Uses the Checkout Session ID as an idempotency key, so Stripe retries do not create duplicate purchase rows.
- Activates six-month coaching only while the Stripe subscription is active or trialling; subscription updates/deletions update access status.
- Marks a purchase refunded after a full refund. Partial refunds do not automatically revoke access.
- Returns a failure status if database processing fails, allowing Stripe to retry.

## 6. Preview test checklist

After setup, use Stripe test mode and a dedicated test client account to test each path:

1. Complete a one-off coaching purchase and confirm a row appears in `client_purchases` with the correct user, product, Checkout Session ID, PaymentIntent ID and `paid` status.
2. Confirm the same account sees its questionnaire and correct Client Hub access.
3. Complete a six-month subscription and confirm the row is `active`.
4. Cancel the test subscription and confirm the row becomes `inactive`.
5. Refund a one-off test payment in full and confirm the row becomes `refunded`.

Do not use production Stripe keys, production Supabase, or real client payments for these tests.
